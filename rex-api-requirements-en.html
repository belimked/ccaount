Conflicts between sources: which one prevails?

3 points. In each, the Rex email and the API docs (including the Integration Guide) say different things, and every method is affected. Each point says what we do for now. Inconsistencies on specific methods (path form, response fields, tag field) are listed under “Not met by Rex · required”.

Initial data load · 1

02-1

Initial data load: all contacts, properties and the relationships between them

Missing in Rex or not enough
What we need
Before launch, a one-off load of three sets of data: every contact in the account, every property in the patch, and the relationships between contacts and properties (who owns or rents which property). After that, a daily incremental update. If Rex does not supply the properties we will use data exported from Pricefinder, in which case each Pricefinder property has to be matched to its Rex property id.
Why
  • Agents working door to door need to see at once who owns a house and when the owner was last contacted. Reception on the street is unreliable and there is a limit of 3,600 requests per hour, so we need a local copy of the data instead of querying Rex every time.
  • All three are needed: contacts without relationships do not tell us which house an owner belongs to; properties without contacts show no owner at the door.
  • Properties exported from Pricefinder may not carry the Rex property id. Without a match the same house appears twice, the owner relationship cannot be attached to the Pricefinder row, and later writes to Rex have no property to point at.
Rex today
  • Contacts::search returns at most 100 rows per page in the default format and can include related.contact_reln_property (contact-to-property relationships), related.contact_tags, phones and emails through extra_options. At 3,600 requests per hour, paging through everything yields at most about 360,000 rows per hour. The docs do not say whether a full pull like this is allowed, or whether the integration account can see every contact in the account.
  • Properties::search is also limited to 100 rows per page and offers contact_reln_property in extra_options; the etags format returns 50,000 rows per page and suits the later incremental reconciliation.
  • Export::queueExport(service_name, criteria, options, output_format) exists and returns the token of an asynchronous task. The docs do not say which services it supports, which output formats exist or how the result file is fetched.
  • Rex can store a link between a Rex property and a Pricefinder property id: ThirdPartyServicePriceFinderPropertyV2::setPropertyRemoteId(connection_id, local_property_id, remote_property_id). The link id is not visible in the Properties data structure or searchable fields, and the docs show no way to read it.
  • Properties::findPossibleDuplicate finds a Rex property by address, one property per call.
  • The docs mark ThirdPartyServicePriceFinderImportV2::queuePropertyImport as Refused: the Domain data agreement allows Pricefinder properties into Rex only by hand, one at a time. Properties that exist in Pricefinder but not in Rex will therefore not be bulk-created in Rex; they stay in our own system only.

Tags · 2

02-6

Contact tags: which field carries them, and grouping by scenario (DK, OFI, Enquiry)

Missing in Rex or not enough
What we need
A scenario attribute on each contact tag, or a convention named by Rex, that tells us which tags belong to DK mode, which to OFI and which to Enquiry. Please also confirm which field contact tags are written to and that this form stays valid.
Why
  • Tags depend on the scenario the contact is met in: door knocking (DK) uses DK tags, an open home (OFI) uses OFI tags, an enquiry uses another set. The agent should be offered only the tags of the scenario they are working in.
  • A tag created by office staff in Rex should also land in the right scenario list without being configured a second time on our side.
  • In all of these scenarios tags are written through Contacts::create / update, so the way tags are written must not stop working.
